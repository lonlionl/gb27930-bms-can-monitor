# GB/T 27930-2015 BMS CAN 监控主终端（I.MX6ULL / Linux SocketCAN）

> 电动汽车非车载传导式充电机与电池管理系统之间的通信协议 —— 充电机侧监控主程序
> 目标平台：野火 I.MX6ULL Pro（Debian，内核自带 SocketCAN）
> 编译平台：Ubuntu 虚拟机 gcc

**本文件是 I.MX 单端使用手册**：模块清单、编译、部署、命令行参数、数据写入策略、
预期输出、数据库查询、单端排查、性能参考、板载基准。
项目总览、GB/T 27930 报文对照表、STM32 端细节与两端合一的联调验证见
[`../项目总使用手册.md`](../项目总使用手册.md)；
STM32 端单独的手册见 [`../STM32_BMS模拟器使用手册.md`](../STM32_BMS模拟器使用手册.md)。

## 一、目录与模块说明

| 文件 | 层次 | 职责 |
|------|------|------|
| `can_layer.c/.h`   | CAN 硬件抽象层 | SocketCAN 封装、rtnetlink 在线配置、CAN 硬件滤波、错误帧分类统计、纳秒时间戳收发 |
| `ring_buffer.c/.h` | 数据缓冲层     | 无锁环形缓冲区（1024 帧），解耦 CAN 接收线程与协议解析线程 |
| `isotp.c/.h`       | 传输层         | ISO 15765-2 与 SAE J1939-21(TP) 双格式多帧重组/发送，支持 BRM、BCP 长报文 |
| `gb27930.c/.h`     | 协议解析层     | 国标报文组包/解析、物理量换算、充电机侧状态机、超时异常处理 |
| `storage.c/.h`     | 数据存储层     | SQLite3（WAL）持久化、无锁写队列、50 帧或 1 秒批量事务提交、历史查询与 CSV 导出 |
| `session.c/.h`     | 数据存储层-历史 | 充电会话表 `charge_session`：只保留最近 9 次，曲线压成 8 字节/点的 BLOB，供九宫格与详情页读取 |
| `ui.c/.h`          | 表现层         | ANSI 彩色终端仪表盘（总线状态 / 状态机 / 实时数据 / 存储统计） |
| `fbdev.c/.h`       | 本地界面-图形  | framebuffer 抽象层：mmap 显存、32 位后台缓冲双缓冲、16/24/32 bpp 自适应、绘图原语、PPM/ASCII 导出 |
| `gui.c/.h`         | 本地界面-布局  | 主界面、数据曲线页、历史九宫格、历史详情页的绘制 + 触摸命中测试；纯数据驱动，可离线渲染 |
| `uitouch.c/.h`     | 本地界面-输入  | evdev 触摸：自动识别设备、兼容 Type A/B 上报协议、坐标映射、按下边沿提取、`demo` 脚本化触摸 |
| `gui_app.c/.h`     | 本地界面-应用  | GUI 线程：数据快照组装、电量积分、触摸切页、历史会话读写 |
| `font16.h`         | 本地界面-字库  | 16×16 点阵字库（自动生成，见 `../tools/gen_font.py --profile linux`），UTF-8 编码，ASCII 95 + 汉字 498。与 STM32 端那份是**两份独立的字库**：STM32 端受 Keil MDK-Lite 的 32 KB 镜像上限约束，只收 `FONT_CJK_COUNT` = 77u 个汉字、GBK 编码，字模 `g_font_data[]` 3984 字节 + GBK 索引表 `g_font_gbk_map[]` 308 字节（合计 4292 字节），改一边不影响另一边 |
| `uitest.c`         | 测试           | 界面离线自检：字库覆盖检查、三屏（主界面 / 数据曲线 / 历史九宫格）渲染成 ASCII 艺术图 + PPM 出图、触摸命中区逐像素扫描 |
| `main.c`           | 调度层         | 命令行解析、三线程创建、信号处理、1 Hz 主循环、优雅停机 |
| `Makefile`         | 构建           | 一键编译、交叉编译、自检、数据库查询、CSV 导出等辅助目标 |
| `selftest.c`       | 测试           | 离线自检程序：**347 条断言**覆盖协议解析、多帧重组、状态机、存储、CAN 错误帧翻译（无需 CAN 硬件） |
| `fake_bms.py`      | 测试工具       | 纯 Python 实现的 BMS 侧模拟器，用于无 STM32 硬件时的端到端联调 |
| `run_e2e_test.sh`  | 测试脚本       | 自动创建 vcan → 启动本程序 + fake_bms → 校验状态机流转与数据库内容 |
| `run_gui_test.sh`  | 测试脚本       | 界面整链路验证：真实数据灌库 + 虚拟屏 + 脚本化触摸 + 逐帧 PPM/PNG + 像素校验 |
| `board_can_diag.sh`| 诊断脚本       | 板上诊断 can0 不存在的全部可能原因（内核配置、设备树、overlay、vcan 可用性） |
| `can_link_test.sh` | 诊断脚本       | 板上 CAN 物理链路排查：控制器状态、回环自测、Bus-Off 观察、不用万用表的短路法 |
| `../tools/bench_board.sh` | 基准测试脚本 | 板上采集性能数据：自配接口，`charging` / `idle` 两种模式（充电中 / 待机）采样 CPU / 内存 / 帧率 / SQLite，见第十一节 |

### 线程模型

```
  ┌────────────────────┐  can_layer_recv()   ┌──────────────────┐
  │ 线程 1             │ ──────────────────► │ 无锁环形缓冲区    │
  │ CAN 接收线程       │                     │ (1024 帧)        │
  │ (实时性最高)       │ ──────────┐          └────────┬─────────┘
  └────────────────────┘           │                   │ rb_pop_batch()
                                   │                   ▼
                                   │          ┌──────────────────────┐
                                   │          │ 线程 2               │
                                   │          │ 协议解析线程         │
                                   │          │ gb27930_process_frame│
                                   │          │ gb27930_tick         │
                                   │          └──────────┬───────────┘
                                   │ storage_push_raw()  │ storage_push_charge()
                                   │ （仅充电会话期间 + 错误帧）
                                   ▼                     ▼
                        ┌───────────────────────────────────────┐
                        │ 存储写队列（无锁 SPSC × 2，各 4096 条）│
                        └───────────────────┬───────────────────┘
                                            │ storage_tick() 每 100 ms
                                            ▼
                                 ┌──────────────────────┐
                                 │ 线程 3  存储线程      │
                                 │ SQLite WAL 批量写入   │
                                 └──────────────────────┘

  ┌───────────────────────────────────────────────────────────────┐
  │ 线程 4  界面线程（默认启动，--no-gui 关闭）                   │
  │   只读 g_can.stats / g_ctx / storage_* 统计量                 │
  │   主界面每 200 ms 重绘，其余页面每 1000 ms，触摸每 30 ms 轮询 │
  │   屏幕 = /dev/fb0；触摸 = /dev/input/eventX                   │
  └───────────────────────────────────────────────────────────────┘
```

## 二、编译（Ubuntu 虚拟机）

### 1. 安装依赖

```bash
sudo apt-get update
sudo apt-get install -y build-essential libsqlite3-dev can-utils \
                        git pkg-config
```

- `build-essential`：gcc / make
- `libsqlite3-dev`：SQLite3 开发库（`storage.c`、`session.c` 依赖）
- `can-utils`：`candump` / `cansend` / `cangen`，联调必备

### 2. 编译

```bash
cd ~/CAN/linux_can_monitor
make                    # 生成 can_monitor
make check              # 编译前自检：确认 gcc / sqlite3.h / can-utils 齐全
make uitest             # 生成界面离线自检程序（不需要屏幕）
```

编译产物为单个可执行文件 `can_monitor`。

> 没有 libsqlite3-dev 权限时：`make` 支持两个变量指定自定义 sysroot，
> 可把 `libsqlite3-dev` 的 deb 包用 `apt-get download` + `dpkg -x` 解到任意目录后使用：
> ```bash
> apt-get download libsqlite3-dev && dpkg -x libsqlite3-dev_*.deb /tmp/sqldev
> make SQLITE_CFLAGS=-I/tmp/sqldev/usr/include \
>      SQLITE_LDFLAGS=-L/tmp/sqldev/usr/lib/x86_64-linux-gnu
> ```

启动监控终端用的命令是：

后面那三个参数都是必需的，缺一个就会出现"看着像程序坏了"的假故障：

| 参数 | 少了它的后果 |
|------|-------------|
| `--auto-start` | **影响最大。** 本程序不会自己上线，只有收到"开始充电"请求后才发 CHM。手动跑时这个请求来自屏上的「充电」按钮；自动化测试里没有人去点按钮，必须靠这个开关把请求置上。少了它，`can_monitor` 一直停在空闲态、一帧 CHM 都不发，`fake_bms.py` 等不到握手只能退出，整条链路一步都走不动。症状是测试大面积 FAIL，数据库里全是 0 条 |
| `-v` | `收到 BRM …` / `收到 BCP …` / `充电机输出准备就绪` 这些逐报文日志只在 verbose 下打印，而第 5 步要靠 grep 这几行判定 J1939 多帧重组是否成功。少了它，状态机仍然走通（握手→辨识→参数配置→充电准备→充电中全部到达），但这三条检查报 FAIL |
| `--no-gui` | 默认 gui=1。CI / 无头机上没有可用的 `/dev/fb0`，不开这个会打出一串 "打开 framebuffer 失败" 的告警 |

脚本里三处都有对应的注释。

两个测试脚本的日志路径都用 `mktemp` 生成（`run_e2e_test.sh` 是 `/tmp/gb27930_*.XXXXXX`，`run_gui_test.sh` 是 `/tmp/gui_*.XXXXXX.log`），不写死成固定的 `/tmp/xxx.log`。原因是这些脚本既可能用 `sudo` 跑、也可能用普通用户跑：固定路径的日志文件如果由 root 建过，普通用户的重定向就会因为权限不够而失败，表现为"编译失败"，而 `make` 根本没有执行。

## 三、部署到 I.MX6ULL 开发板

### 0. 硬件前提（CAN 不通先查这里）

#### ① CAN 收发器电源跳线 J8（必须短接）

野火 EBF6ULL B1 Pro 底板上两个 TJA1042T/3 收发器共用一条独立电源轨 `CAN_3V3`，
这条轨经 J8（2×4 排针，丝印标注「CAN1和CAN2的电源」）供电，**出厂默认不接**。
只有用跳线帽把 **J8 的 1、2 脚短接**（3V3 → CAN_3V3），收发器才有电。

- 跳线位置：板上丝印 `J8`，2×4 排针（8 个针，2.54 mm 间距）。
- 紧挨着有一个外形完全一样的 `J7`，那是 RS485 的电源，**不要插错**。
- 断电后再插拔跳线帽；没有跳线帽时用一根母对母杜邦线短接 1、2 脚也能验证。

没插跳线时的症状是**收发器无电、总线上等于没有节点**，而 FlexCAN 控制器本身完全正常：

| 位置 | 现象 |
|------|------|
| i.MX | `接收 0 帧`、`错误帧` 只有 BUSOFF/RESTARTED，`dmesg` 反复 `flexcan 2090000.can can0: bus-off`；`candump` 一帧也抓不到；只有控制器内部回环（`loopback on`）能收到自己发的帧 |
| STM32 | 每秒 `CAN总线: TEC=128 REC=0 LEC=3(ACK错误(无人应答))`、`收 0 帧`；只有 ACK 错误，没有位错误/填充错误/格式错误 |
| 与接线错误的区别 | 接反或断线时 STM32 也报 ACK 错误；**收发器无电时 i.MX 的 rx 计数恒为 0，且 CAN1↔CAN2 两板对插也不通** |

对端 STM32 侧的引脚固定：CAN1_RX = **PA11**、CAN1_TX = **PA12**（板载 TJA1050），
本端则是 FlexCAN 的 `can0` / `can1`；两端 CANH↔CANH、CANL↔CANL 同名相连。

排查时可用的两条判据：

```bash
# 控制器内部自环：收发器没电也能通过，通过说明驱动/控制器没问题
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 250000 loopback on
sudo ip link set can0 up
timeout 4 candump can0 & sleep 1
cansend can0 1826F456#0100010000000000     # 应当能 dump 到自己发的帧

# 插上 J8 跳线、恢复正常模式后，STM32 空闲态每秒发一帧非国标 ID 心跳 0x18FFF4F4
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 250000 restart-ms 100 loopback off listen-only off
sudo ip link set can0 up
timeout 6 candump -e can0                  # 收到每秒一帧 18FFF4F4 即说明收发器正常
```

#### ② 设备树插件与端子对应关系

曲线区的具体行为：

- 一排四个指标切换按钮：`电压 V`、`电流 A`、`温度 C`、`电量 %`，位于 y=48 一行，
  每个 110×18（x 起点为 8、123、238、353）。点按钮只重绘曲线与底部统计，页面不变；
  数据曲线页与历史详情页都有这一排，选中项蓝底高亮。
- 横轴不是时间轴，而是**电量增量**：起始 SOC 对应绘图区最左边，横轴内部按
  0→100% 分成 1000 份，所以从 45% 充到 100% 只占左边 55%，右侧留空；
  不管从多少电量开始充，曲线都从最左边开始向右生长。
- 横轴刻度上不写电量，绘图区正下方只有一行起止时间 `HH:MM:SS->HH:MM:SS`：
  左边是本次充电首点时间，右边是最后一个采样点（充电中就是当前时刻，一直在走）；
  没有数据时显示 `--:--:-->--:--:--`。
- 纵轴每条曲线有固定内定量程，不随数据自适应（自适应会把整段数据拉满高度，
  看上去就是一条从左下到右上的斜线）：电压 400~600 V（蓝）、电流 0~120 A（橙）、
  温度 0~60 ℃（黄）、电量 0~100%（绿）。左侧 5 档刻度写当前指标的量程数值。
  超出量程的点贴着上下边画，不裁剪。
- 底部统计行格式为 `电量 x.xx kWh    <指标名> 实测 起始值 -> 结束值`，四个指标随按钮切换
  同步更新；电量这一条结束时取本次会话见过的最高电量（BMS 在 SOC 到 100.0% 那一拍就
  停发 BCS，末点常常只剩 99.x%，取最高值才不会显示成 99）。
- 历史九宫格的缩略图按**电量的绝对位置**绘制，横坐标 = 电量 0~100% 铺满格宽：
  从 50% 充到 75% 就从格子正中间画到四分之三处，从 0% 充到 100% 正好铺满整格；
  两头各立一根小柱（灰 = 起始电量，绿 = 结束电量）。数据曲线页和历史详情页的主图
  不受影响，仍从最左边开始画。
- 主界面的充电按钮是同一个按钮的两种身份：待机（或放电中）时显示高亮的「充电」，
  充电流程中显示红底「停止」。按下后立刻生效，互锁窗口只有 800 ms（用来滤掉一次
  点击重复投递的触摸事件），所以按下「停止」的瞬间按钮就变回「充电」。
- 会话记录只保留最近 9 次（不含正在进行的这一次），存在同一个数据库的
  `charge_session` 表里。正常结束与充电中途被结束（Ctrl+C / `kill -TERM`）都会写进这张表，
  区别只在 `is_full` 标志（见第四节）。

界面相关命令行参数（均为长选项）：

| 参数 | 说明 |
|------|------|
| `--gui`        | 启用本地屏幕界面（默认已启用，此参数用于显式打开） |
| `--no-gui`     | 关闭本地屏幕界面，只跑终端仪表盘 |
| `--fb <dev>`   | framebuffer 设备，默认 `/dev/fb0`；传 `virtual` 使用内存虚拟屏（没有屏幕的机器上也能跑通整条界面链路） |

| `--gui-rec <dir>` | 把渲染的每一帧导出到该目录（PPM），文件名 `NN_main.ppm` / `NN_curve.ppm` / `NN_grid.ppm` / `NN_detail.ppm`；隐含启用界面 |

#### 板子上跑着桌面（X11）时的表现

野火 Debian 出厂是带桌面自启动的。只要 X 在跑，就会出现三个同一来源的症状：

| 症状 | 原因 |
|------|------|
| 界面时不时闪回系统桌面 | 桌面进程也在往 `/dev/fb0` 上绘制，把本程序的帧盖掉 |
| 触摸按钮点不动 | 桌面已经打开了触摸的 `event` 设备并消费事件，本程序收不到 |
| Ctrl+C 退出时进程卡住不返回 | 退出时要等一个被 Xorg 占着的资源 |

程序启动时会检测 `/tmp/.X11-unix`，**检测到桌面就自动独占抓取触摸设备**
（这条自动抓取的说明只在 `-v` 时打印，产品形态下不再往串口里灌桌面冲突提示）。
不需要自动抓取时用 `--no-touch-grab`。

```bash
# ① 停掉桌面再跑（屏幕和触摸都归本程序，不会闪、不会卡）
sudo systemctl stop lightdm        # 也可能是 gdm3 / nodm / sddm
# 若桌面是 startx 起的：
sudo pkill -x Xorg
sudo ./can_monitor -i can0 -b 250000

# ② 不停桌面，只把触摸抢回来（屏幕仍可能偶尔被盖）
sudo ./can_monitor -i can0 -b 250000 --touch-grab

# ③ 只验证界面逻辑：虚拟屏 + 脚本化触摸，不影响桌面
sudo ./can_monitor -i can0 --fb virtual --touch demo \
     --gui-rec /tmp/frames -r 12
```

`--touch-grab` 用的是内核的 `EVIOCGRAB` 独占锁，只影响该 event 设备
（鼠标键盘是别的设备，不受影响）；程序退出时会自动释放，不会把桌面的触摸永久弄坏。

**排查屏幕问题**：

```bash
ls -l /dev/fb*                 # 有没有 framebuffer 节点
cat /proc/fb                   # 内核识别到了哪块屏、什么格式
fbset -i                       # 分辨率 / 位深 / 步长（没有 fbset 可 apt 装）
cat /proc/bus/input/devices    # 触摸设备的 event 号与设备名
sudo ./can_monitor -i can0 --fb /dev/fb0 --touch /dev/input/event1
```

**屏幕没显示或设备树没配**：先看 `cat /proc/fb`（有没有 framebuffer）与
`cat /proc/bus/input/devices`（有没有触摸节点），两个都空才去查 overlay 配置。
CAN 侧的设备树插件（`imx-fire-can1/can2.dtbo`）在项目总手册
[`../项目总使用手册.md`](../项目总使用手册.md) 的
「六、联调验证步骤」步骤 0 里。

这 15 条通过项覆盖：接口就绪、编译通过（判据是 `make` 退出码 0；编译日志里出现 warning 会单独报一条 FAIL，Ubuntu 18.04 + gcc 7.5.0 下实测 0 warning）、`charge_data` 写入 13 条解析记录（判据 > 3）、界面线程启动、虚拟 framebuffer 渲染、导出 19 帧（判据 >= 5）、主界面帧 10 张、触摸触发「主界面→数据曲线」恰好 1 次、再触发「数据曲线→历史九宫格」恰好 1 次、数据曲线帧 3 张、历史九宫格帧 6 张、点空白区未误触发、PNG 转换成功、数据曲线帧绘图区内出现曲线颜色的像素（判据 >= 1）、主界面帧非背景像素（判据 > 2000）。

#### 曲线判据：判据区与颜色

判据区一旦包含指标按钮行，「曲线已画出」这条断言就是恒真的：选中的指标按钮用 `FB_COL_BLUE` 实心填充，而 `FB_COL_BLUE` 同时是「电压 V」曲线的颜色，于是一个采样点都没有时也能统计到上千个像素（`diag_metric_row` = 1564，全部来自选中按钮的填充，同一轮里真正的曲线读数 `curve_px` = 17）。判据涉及的几何与颜色：

| 项 | 取值 | 依据 |
|----|------|------|
| 指标切换按钮行 | y 48..65（含 1 像素边框），x 8..462 | `gui.c` 的 `MBTN_Y` = 48、`MBTN_H` = 18、`MBTN_X0` = 8、`MBTN_W` = 110 |
| 曲线绘图区 | x 58..472，y 70..200 | `gui.c` 的 `CURVE_X0/X1` = 58/472、`CURVE_Y0/Y1` = 70/200 |
| 选中按钮的填充色 | `FB_COL_BLUE` = `4C 9A FF` | `draw_metric_bar()`，默认选中「电压 V」 |
| 「电压 V」曲线的颜色 | `FB_COL_BLUE` = `4C 9A FF` | `g_metric[GUI_METRIC_V].color` |

现在的判据由三部分组成：

- **判据区只取绘图区** `(58,70)-(472,200)`，指标按钮行在区外；
- **统计的是颜色**「属于四条曲线颜色（`4C 9A FF` / `FF 9A 3D` / `F2 C1 4E` / `3D D6 8C`）的像素」，不是「高饱和像素」；
- **阈值 `curve_px >= 1`**。

为什么这样能区分「有曲线」和「曲线为空」：曲线为空时走的是 `gui.c` 的空态分支（`n == 0`），绘图区里只画网格线 `FB_COL_BORDER`、左侧刻度与提示文字 `FB_COL_DIM`，没有一个是曲线颜色，读数恒为 0；采到采样点时 `draw_series_metric()` 至少画一个点（1 个点走 `fb_pixel()`、2 个点以上走 `fb_polyline()`），用的就是 `g_metric[m].color`，读数至少为 1。绘图原语直接写 RGB、不混色也不抗锯齿（`fbdev.c` 的 `fb_pixel()` / `fb_line()`），所以帧里的颜色与上表常量**精确相等**，不存在"近似色判不出来"的中间地带。

阈值不写成 `> 200` 这类大数字：本轮 `-r 11`，数据曲线页只在触摸演示的 2 s ~ 5 s 之间显示，横轴又是电量增量，切页窗口内通常只有 2 ~ 5 个采样点，光栅像素数是 `4n - 3` 的量级（n = 2 → 5、n = 3 → 9、n = 4 → 13、n = 5 → 17）。阈值取 1 是靠颜色与判据区把"空"和"非空"分开，而不是靠像素数量。

第 4 步的 `can_monitor` 同样带 `--auto-start`，原因见第三节第 5 小节那张参数表：程序不会自己上线，只有收到"开始充电"请求才发 CHM，而 `fake_bms.py` 要等到 CHM 才开始握手。少了它，这一轮从头到尾停在待机，数据曲线页走空态分支（`gui.c` 画「尚未开始充电，点主界面『充电』」），曲线判据会如实报 FAIL。

日志路径全部由 `mktemp` 生成（`/tmp/gui_mon.XXXXXX.log` 等）。原因是这些脚本既可能用 `sudo` 跑、也可能用普通用户跑，固定路径的日志文件如果由 root 建过，普通用户的重定向就会因为权限不够而失败，表现为"编译失败"，而 `make` 根本没有执行。

触摸演示脚本（`uitouch.c` 的 `DEMO_SCRIPT`）按标称时刻产生三次「按下」，计时自 `uitouch_open()` 起算，实际触发时刻受 30 ms 触摸轮询粒度影响：

| 标称时刻 | 坐标 | 预期 |
|------|------|------|
| 2 s | (357, 14) | 主界面「数据曲线」按钮（x 314..401） |
| 5 s | (366, 14) | 数据曲线页「历史」按钮（x 332..401） |
| 8 s | (200, 270) | 九宫格与标题栏之外的空白带，不应有任何切页 |

脚本靠日志里有没有出现 `-> 数据曲线`、`-> 历史记录`、`演示脚本第 3 步` 来判断，
所以启动 `can_monitor` 时**必须带 `-v`**（这些逐条日志默认不打印）。

三个参数各自解决一个「没有硬件也能验」的问题：

| 参数 | 解决的问题 |
|------|-----------|
| `--fb virtual` | 没有 `/dev/fb0` 时，界面渲染到一块内存里的 480×272 屏上（`fb_open_virtual()`），绘制代码与真屏完全一致，只是最后不写显存 |
| `--touch demo` | 没有触摸设备时，`uitouch.c` 按标称时刻产生三次「按下」事件。演示模式不打开任何设备节点（`fd` 保持 -1）、不调用 `EVIOCGRAB`，因此触摸这一段不需要 root，也不依赖 `/dev/uinput`；它跳过了设备节点打开、evdev 事件解析、坐标映射（`map_axis()` / `finalize_coords()`）三段，坐标直接取屏幕坐标（`raw_x/raw_y` 与 `x/y` 同值），`--touch-swap` / `--touch-mirror-*` / `--touch-calib` 对演示坐标无效。切页之后的重绘仍走真实路径：`handle_touch()` 取按下边沿 → `gui_hit_test()` 命中测试 → 切换 `g_gui.screen` → 按当前页绘制（数据曲线页画的是内存里本次充电的采样点；点到「历史」时经 `hist_reload()` 读 SQLite 的 `charge_session` 表） |
| `--gui-rec <dir>` | 屏幕上的东西只有在板子上才看得见，导出每一帧后就能在电脑上目视检查；默认最多导 24 帧 |

## 四、数据写入策略

- `can_raw`（原始帧）**只在充电会话进行中才写**：`main.c` 的接收线程里判断
  `if (g_can_stat_enable || item.is_error)`，而 `g_can_stat_enable` 由协议线程按
  `(dump 模式 || 状态 != IDLE)` 翻转。待机的 BSM / 心跳属于周期遥测，对事后分析没有
  价值却会把库撑大（实测跑 7 分钟 887 帧原始记录里 215 条才是有效充电报文），
  所以不入库；**错误帧例外，任何时候都保留**作为证据。
- `charge_data`（解析记录）在 `状态 >= PARAM_CONFIG 且 != FAULT` 时每秒写一条，
  用于事后还原电压/电流/SOC/温度曲线。
- `charge_session`（会话历史）**两种结束方式都会写一条**，只保留最近 9 次，超出就删最旧的：
  正常结束（BMS 发 BST 收尾，或状态机回到空闲态，含用户按「停止」）由 GUI 线程的
  `snapshot_build()` 调 `curve_finish()` 写入；程序在充电**进行中**被结束（Ctrl+C /
  `kill -TERM` / 关机）由优雅停机路径 `gui_app_stop()` 补调一次同一个 `curve_finish()` 写入，
  位置在 `pthread_join` 之后 —— 线程停了曲线数据才不会变。`curve_finish()` 内部用
  `cur_saved` 去重，正常结束已经存过的那次不会被补存第二遍。两路写入都带 `is_full` 标志：
  `1` = 充满结束，`0` = 中途结束。现场最典型的就是「中途拔枪」—— 不想充了直接停掉程序，
  而这次充电停在多少电量恰恰是要看的。
- 上面那条补存有两个前提，缺一条就不会留下记录：曲线采集（`curve_push()`）在 GUI 线程里，
  所以 `--no-gui` 启动时既不采曲线也不写 `charge_session`（`gui_app_stop()` 会因
  `g_gui.running == 0` 提前返回），正常带屏运行不受影响；`kill -9` 强杀走不到优雅停机路径，
  同样不留记录，这一点无法避免。
- 批量提交条件是「暂存累计 50 条」或「距上次提交 1000 ms」或「暂存区满」，
  三者任一满足即整批落盘。

## 八、常见问题排查

### CAN 与硬件

收发器无电、`接口 can0 不存在`、`operstate` 显示 `UNKNOWN`、永远不发 ACK、
在线配置报 `Device or resource busy` 这几类原因的完整排查表见项目总手册
[`../项目总使用手册.md`](../项目总使用手册.md) 的
「七、故障排查速查表」（7.1 错误帧日志解读 / 7.2 界面相关）。

本端特有的排查项：

| 现象 | 原因 | 处理 |
|------|------|------|
| 错误帧计数持续增长、TEC 上升 | 波特率不一致或线序接反 | 两端都必须是 250 kbps；CANH↔CANH、CANL↔CANL；要换极性**只能在某一端对调**（两端同时换等于没换） |
| 总线无 ACK、发不出去 | 缺 120Ω 终端电阻或只有单端 | 断电测 CANH–CANL 应为 60Ω；或用 `loopback on` 自测 |
| 线接好了还是不通，怀疑线本身断 | — | `bash can_link_test.sh can0`，用短路法（把 i.MX 端 CANH/CANL 短接，看 STM32 的 REC/LEC 有没有变化）判断 |
| 线插在 CAN2 座却仍是 `can0 UP` | 接口名与物理端子无关，另外 can1 可能没配置过 | 端子对应关系见第三节；两个口都要 `down → type can ... → up` |
| 屏幕一直乱闪、充电状态反复乱切换 | 对端 BSM 报文洪水灌满总线（可达上千帧/秒），1024 帧环形缓冲持续溢出 | `timeout 2 candump can0 \| wc -l` 看总线帧率，正常应是每秒几帧到几十帧（实测充电中 51 帧/秒、待机 5 帧/秒），一千多帧/秒属于对端固件异常 |
| 对端 STM32 屏幕红灯常亮、「异常」一行显示 `CAN 总线 Bus-Off` | 对端检测到总线关闭，进了故障态 | 这是 STM32 的预期行为：Bus-Off 走 `EnterError()` 进 `BMS_ST_FAULT`，10 秒后由 `BMS_Protocol_Reset()` 自动复位回空闲态并重新等 CHM；红灯亮着的那 10 秒不用干预，超过 10 秒还回不来再查线 |

### 界面

桌面（X11）抢触摸、屏幕闪回桌面这两类现象见项目总手册
[`../项目总使用手册.md`](../项目总使用手册.md) 的 7.3 节
（本文件第三节第 5 小节也有同一条处置办法）。

| 现象 | 原因 | 处理 |
|------|------|------|
| 点「数据曲线」/「历史」进去后还能看到上一页的数字 | 页面进入时未清屏（`fb_clear()` 缺失） | 每个页面入口都调用 `fb_clear()`；出现残影说明板上二进制与源码不一致 |
| 点按钮没反应 | 触摸被 X11 桌面消费；或触摸量程不对；或点在按钮外面 | 加 `--touch-debug` 看有没有收到触摸；停掉桌面或自动抓取触摸；量程用 `--touch-calib` 校正 |
| 触摸坐标全挤在左上角一小块 | 内核上报的原始量程与屏幕分辨率不一致 | 本屏实际量程为 `0,474,0,272`（X 用 474），已是程序默认值 |
| 点「充电」没反应，或充过一次后再也点不动 | 请求开始被静默丢弃（`FAULT` 态直接 return） | 置开始请求前先把状态机复位回 IDLE，日志里打印 `从 xxx 状态重新开始充电` |
| 按「停止」后 STM32 停一下又开始充电 | 一次点击在事件队列里留下多个「按下」事件，第二个被当成「充电」 | `handle_touch()` 处理一个动作就退出，并有 800 ms 互锁 |
| 按「停止」要等几秒按钮才变回「充电」 | `STOPPING` 被算作「还在充电」 | 按钮在按下瞬间就切回「充电」，防误重启交给协议层 5 秒窗口 |
| 历史里每次都显示充到 99、充满被记成「中途结束」 | BMS 在 SOC 到 100.0% 的那一拍就停发 BCS，末点只剩 99.x% | 按会话见过的最高电量判定与存储，`[99.0,100]` 统一归到 100 |
| 中文显示空白或缺笔画 | 界面文案里的字不在 `font16.h` 里 | `make uitest && ./uitest`，缺字会直接列出来；补进 `../tools/gen_font.py` 的扫描列表后重新生成字库 |
| 曲线被拉成一条固定高度的斜线 | 纵轴按数据自适应 | 每条曲线用固定量程（电压 400~600V 等），不随数据缩放 |
| 切到历史页要顿一下 | 进入历史九宫格时在触摸回调里同步查一次 SQLite（`hist_reload()` → `session_list()`） | 界面线程每 1000 ms 在后台刷一次同一份列表（`GUI_CURVE_BG_MS`）；这条查询只取 `charge_session` 的最近 9 条元信息（`SESSION_MAX` = 9），行数不随运行时长增长 |

### 存储与构建

| 现象 | 原因 | 处理 |
|------|------|------|
| 数据库写入慢 | 逐条自动提交 | 本程序已用 WAL + 50 条/1 秒批量事务 |
| 数据库原始帧数虚高 | 待机遥测（BSM / 心跳）也会入库 | 只在充电会话期间存原始帧，错误帧例外 |
| 改了代码但板上行为没变 | 板上跑的是与源码不一致的二进制；或多层目录副本导致编的不是同一份源码 | `ls -d /root/CAN/CAN` 查嵌套；`grep -c 'auto-start' main.c` 查源码是否为当前版本；`make clean && make` 后比对时间戳 |
| 板上二进制大小和虚拟机不一致 | 板上用板载 gcc、虚拟机用 x86 gcc，大小本来就不会一样 | 比对源码 md5，不要比二进制大小 |

本节全部是板载实测，采集脚本是 `tools/bench_board.sh`（见第十一节）。

实测环境：

```
内核        Linux 4.19.35-imx6
硬件        Freescale i.MX6 UltraLite (Device Tree)
CPU         ARMv7 Processor rev 5 (v7l) @ 792 MHz，单核
内存总量    486.6 MB
CLK_TCK     100
CAN 位定时  bitrate 250000
```

### 充电中与待机工况实测

| 指标 | 实测值 | 采样条件 |
|------|--------|----------|
| 总线帧率 | **51 帧/秒** | 充电中，60 秒采到 3114 帧；脚本用整数除法显示为 51，3114÷60 = 51.90 |
| 总线帧率（待机） | **5 帧/秒** | 待机，60 秒采到 300 帧（`idle` 模式实测） |
| 总线负载 | **3.11 %** | 充电中，按每帧约 150 位估算 |
| 总线负载（待机） | **0.30 %** | 待机，按每帧约 150 位估算（`idle` 模式实测） |
| 进程 CPU 占用 | **4.9 %** | 充电中，单核百分比 |
| 进程 CPU 占用（待机） | **1.9 %** | 待机，单核百分比 |
| 内存 RSS | **2244 KB** | 充电中、无 GUI |
| 内存 RSS（待机） | **2056 KB** | 待机、无 GUI |

| CAN 错误帧 | **0** | 位错误 / 填充 / 格式 / ACK / CRC 全为 0 |
| SQLite 全表扫描 | **3875 条/秒** | `charge_data` 全表聚合查询，脚本读数 32 ms |
| TF 卡顺序写 | **30.4 ~ 30.6 MB/s** | `dd bs=1M count=32 conv=fdatasync` |
| 数据库增长速率 | **8.3 MB/小时**（按充电阶段计） | 按 `86.5 字节/行 × 27.9 帧/秒` 折算；待机不入库、增长为 0 |
| 数据库原始帧（待机） | **0 帧** | 待机，遥测不入库 |
| 串口输出（对端 STM32） | 28 行/秒（115200 下约 11% 占用） | 按周期推算 |

采样窗口内各 ID 的帧数：CCS `0x1812F456` 1199 帧、BCL `0x181056F4` 1197 帧、
CRO `0x100AF456` 240 帧、BCS `0x1C1156F4` 239 帧、BSM `0x181356F4` 239 帧，
合计 3114 帧，正好等于窗口内的总帧数，说明这个窗口里没有采到其他 ID 的报文。

握手阶段的一次性报文（BHM / BRM / BCP / BRO / TP.CM / TP.DT）不在这 60 秒窗口内，所以不在这个统计里。

待机时的总线构成（`idle` 模式实测，60 秒窗口）：

```
   240 帧  0x181356F4   BSM 电池状态（4.0 Hz，不分状态全局广播）
    60 帧  0x18FFF4F4   非国标心跳（1.0 Hz，仅空闲态发）
```

两路相加 240 + 60 = 300 帧，正好等于窗口内的总帧数（5 帧/秒），窗口里没有第三个 ID：
待机时本端一帧 CHM / CRO 都不发，STM32 也不发 BCL / BCS。

待机态 `can_monitor` 的退出统计：运行 124 秒、接收 0 帧、发送 0 帧、错误帧 0
（位错误 / 填充 / 格式 / ACK / CRC 全为 0）、解析报文数 500、数据库原始 0 帧 / 解析 0 条；
`can_raw`、`charge_data`、`charge_session` 三张表都是 0 条，数据库体积 32 KB（空库）。

两条限定：

- **「250 kbps 总线理论最大帧率」是推算值，不是实测值。** 按扩展帧 8 字节数据、含位填充开销约 150 位估算：`250000 ÷ 150 ≈ 1600~1700 帧/秒`。这个数只用于衡量 51 帧/秒的工作点离总线天花板有多远。
- **这些数字测的是本工程的工作点，不是总线吞吐能力。** 对端是 STM32 模拟器，报文周期按 GB/T 27930-2015 取值，所以帧率是 51 帧/秒、负载 3.11 %。要测极限吞吐需要用 `cangen` 之类的工具把总线打满，本项目没有做这项测试。

### 报文周期实测

各 ID 的帧数取自同一块 I.MX6ULL 开发板上 60 秒充电窗口的实测计数；
周期 = `60000 ÷ 帧数`，保留两位小数。

| 报文 | ID | 发送端 | 帧数 / 实测周期 | 标准周期 | 偏差 |
|------|----|--------|----------------|----------|------|
| BCL 电池充电需求 | `0x181056F4` | STM32 | 1197 帧 / **50.13 ms** | 50 ms | 一致 |
| CCS 充电机充电状态 | `0x1812F456` | i.MX | 1199 帧 / **50.05 ms** | 50 ms | 一致 |
| BCS 电池充电总状态 | `0x1C1156F4` | STM32 | 239 帧 / **251.0 ms** | 250 ms | 见下方窗口边界说明 |
| BSM 动力蓄电池状态信息 | `0x181356F4` | STM32 | 239 帧 / **251.0 ms** | 250 ms | 见下方窗口边界说明 |
| CRO 充电机输出准备就绪 | `0x100AF456` | i.MX | 240 帧 / **250.0 ms** | 250 ms | 一致 |
| **合计** | | | **3114 帧**（60 秒，51 帧/秒） | | |

BCS 与 BSM 的 239 帧来自采样窗口边界而非周期漂移：计数器窗口略短于 60.000 秒，
标称 240 帧的报文在略短的窗口里采到 239 属正常；周期一律按 `60000 ÷ 帧数` 换算，
所以 239 帧对应 251.0 ms、240 帧对应 250.0 ms。

CRO 与 CHM / CRM / CML 同为 250 ms（`T_CRO_PERIOD_MS` = 250u）。CTS 是参数配置阶段的时间同步报文、
不进充电阶段，60 秒窗口里五个 ID 的帧数相加 1199 + 1197 + 240 + 239 + 239 = 3114，
正好等于窗口内的总帧数，说明这个窗口里一帧 CTS 都没有采到；`T_CTS_PERIOD_MS` 只做了编译与自检层面的验证。
CCS 是充电阶段唯一会出现的扩展报文；BEM / CEM 只在故障态 / 超时路径上按 250 ms 连发，
正常充电全程 0 帧。

`charging` 模式在同一块开发板上按 60 秒窗口重复采样，BSM / BCS / CRO 三个报文的帧数完全相同，
BCL 与接收帧数相差 1.4 ~ 1.5 %，说明对端 STM32 的报文周期稳定，51 帧/秒这个工作点可以重复采到。
SQLite 全表扫描随当时的系统负载变化明显（同一份代码先后测得 4133 / 4629 / 3378 / 3875 条/秒），
按 **3875 条/秒** 记。

### 数据库增长

充电阶段每次入库实测都使用全新空库、由 `--auto-start` 发起充电、只取充电阶段，
三次实测的合计值：

| 实测 | 窗口 | 数据库字节 | `can_raw` | `charge_data` | 行数合计 |
|------|------|-----------|-----------|---------------|---------|
| ① | 300 秒 | 471,040 | 5473 条 | 203 条 | 5,676 |
| ② | 100 秒 | 249,856 | 2693 条 | 99 条 | 2,792 |
| ③ | 90 秒 | 233,472 | 2481 条 | 89 条 | 2,570 |
| **合计** | — | **954,368** | **10,647** | **391** | **11,038** |

单轮折算的每行成本在 83.0 ~ 90.8 字节/行之间摆动，差额来自各轮 SQLite 页填充率不同；
报数时用三次加权平均的 **86.5 字节/行**，它与采样窗口无关。

```
每行成本 = 954,368 字节 ÷ 11,038 行 = 86.5 字节/行

充电阶段入库帧率 = BCL 19.95 + BCS 3.98 + BSM 3.98 = 27.9 帧/秒
                  （这三个报文都在充电阶段入库；发送侧的 CCS / CRO 不入库）

充电阶段增长 = 27.9 帧/秒 × 3600 秒 × 86.5 字节/行 = 8,688,060 字节/小时
             = 8,688,060 ÷ 1024 ÷ 1024 ≈ 8.3 MB/小时
               （本项目统一按 1024 换算，与固件 27408 字节 = 26.77 KB、
                 数据库 249,856 字节 = 244 KB 的口径一致）
```

27.9 帧/秒 取自同一 60 秒窗口内的 BCL 1197 帧、BCS 与 BSM 各 239 帧，
是实测值；三次入库实测窗口合计 490 秒，不入本式计算。

增长速率按「字节/行 × 帧率」计算，不使用「数据库体积 ÷ 采样时长」：握手 / 辨识 /
参数配置 / 结束态都不入库，而建表的固定开销又被平摊进时长，同一个库只换窗口就会
算出差近一倍的值（300 秒那轮 5.4 MB/小时、100 秒那轮 8.6、90 秒那轮 8.9）。
报这个数时注明「按充电阶段计」。

两个可交叉验证的口径：

- **每行成本 86.5 字节**（954,368 ÷ 11,038 行 = 10,647 + 391），与时长无关，是最稳健的指标。
- **收发帧率对得上**：接收约 **27 ~ 28 帧/秒** = BCL 19.95 + BCS 3.98 + BSM 3.98 = 27.91；
  发送约 **23 帧/秒** = CCS 20.00 + CRO 4.00 ≈ 24。

充电速率固定：`SIM_SOC_STEP_X10 = 5` 即每秒 +0.5 %，1 秒一拍；SOC 跨会话存在 STM32 的 Flash 里，
除首次上电外起始 SOC 都接着上一轮，不一定是出厂值 45 %。

### 周期取值与有意保留的扩展

报文周期按 GB/T 27930-2015 的国标值：

| 宏 | 位置 | 值 | 国标 |
|----|------|-----|------|
| `GB_T_BCL_PERIOD` | `User/Bms/bms_protocol.h` | 50u | 50 ms |
| `GB_T_BCS_PERIOD` | `User/Bms/bms_protocol.h` | 250u | 250 ms |
| `GB_T_BSM_PERIOD` | `User/Bms/bms_protocol.h` | 250u | 250 ms |
| `T_CTS_PERIOD_MS` | 本端 | 500u | 500 ms |

有意保留、与国标有差异的扩展：

| 扩展 | 与国标的差异 | 为什么保留 |
|------|--------------|------------|
| BSM 不分状态广播 | 国标只在充电阶段发 BSM，本工程待机 / 充满 / 掉电阶段也一直发 | i.MX 相当于车机上的电池监控软件，非充电状态也要看到实时电量；待机帧不入库，不撑大数据库 |
| 心跳报文 `0x18FFF4F4` | 非国标 ID，1 Hz，只在空闲态发 | 让本端一条 `candump` 就能确认物理链路通不通，不需要万用表 |
| J1939 TP 超时统一取 1000 ms | J1939-21 规定 T1=750 / T2=1250 / T3=1250 / T4=1050 四个独立定时器，本工程简化为单一 `T_ISOTP_MS` = 1000 ms | 功能上可用，不是逐字对齐标准 |
| BMS 不主动上线 | 本程序这一侧（充电机）发起 CHM，BMS 只被动响应 | 主从分工：i.MX 是主站，STM32 是从站 |

对 I.MX 端而言，周期变快只影响接收侧的帧数与入库量：解析、状态机、超时判据都不依赖
对端的发送周期。

**编译告警口径**：Linux 端 `make` 在 Ubuntu 18.04 + gcc 7.5.0 下为 0 error / 0 warning；
板子 Debian 10 的较新 gcc 会额外报 2 个 `-Wformat-truncation`，属既有代码：

```
ui.c:401:29: warning: '%s' directive output may be truncated writing up to 255 bytes
              into a region of size between 179 and 210 [-Wformat-truncation=]
gui.c:313:86: warning: '%s' directive output may be truncated writing up to 63 bytes
              into a region of size between 11 and 49 [-Wformat-truncation=]
```

STM32 端为 Keil `0 Error(s), 0 Warning(s)`；固件体积
`Code=21264 RO-data=5908 RW-data=236 ZI-data=2572`，Total ROM

## 十一、板载基准测试（`tools/bench_board.sh`）

第十节的性能数据由该脚本采出。脚本在 I.MX6ULL 开发板上跑，自己配置 CAN 接口，
有 `charging`（充电中）与 `idle`（待机）两种采样模式，输出一段可以直接复制粘贴的表格。

```sh
cd ~/CAN && make
sudo sh tools/bench_board.sh can0 60          # 接口名 + 每个采样的秒数；第三参数省略时是 charging
sudo sh tools/bench_board.sh can0 60 charging # 充电中：加 --auto-start，本程序主动发起充电
sudo sh tools/bench_board.sh can0 60 idle     # 待机：不加 --auto-start，两端都停在待机
```

两种模式的区别只有一个参数 —— 是否给 `can_monitor` 加 `--auto-start`：

| 模式 | `--auto-start` | 采到的是什么 |
|------|----------------|--------------|
| `charging`（默认） | 加 | 本程序主动发起充电，采的是充电阶段的工作点：报文密、负载高（51 帧/秒、负载 3.11 %、进程 CPU 4.9 %、内存 RSS 2244 KB） |
| `idle` | 不加 | 本程序停在空闲态、STM32 也停在待机，采的是待机流量：心跳 1 Hz + BSM 4 Hz（5 帧/秒、负载 0.30 %、进程 CPU 1.9 %、内存 RSS 2056 KB） |

脚本内部用 `MODE=${3:-charging}` 和 `AUTO` 变量实现，【2】【3】【4】三节的标题与结尾提示都会带上当前模式。
60 秒窗口下 `charging` 收到 3114 帧、`idle` 收到 300 帧。

脚本依次做七件事：

| 段 | 内容 |
|----|------|
| 【0】 | 环境信息：日期、内核、硬件、CPU 型号与核数、当前频率、内存总量、`CLK_TCK` |
| 【1】 | 把接口配成 250 kbps 并 up，打印接口状态与 `ip -details` 里的位定时 |
| 【2】 | 按模式启动 `can_monitor`（`charging` 加 `--auto-start`，`idle` 不加），打印启动后的状态 |
| 【3】 | 连续数 N 秒 `candump`，给出总线帧率、按每帧约 150 位估算的总线负载、各 ID 帧数前 12 |
| 【4】 | 同一次运行里采进程 CPU（读 `/proc/PID/stat` 的 utime+stime 除以 `CLK_TCK`）与内存 RSS |
| 【5】 | 发 SIGTERM 优雅退出，抓程序自己的退出统计（运行时长 / 接收 / 发送 / 错误帧 / 解析 / 数据库） |
| 【6】 | SQLite：`can_raw` / `charge_data` / `charge_session` 记录数、库体积、一次全表聚合的耗时与条/秒（脚本用 `--no-gui` 启动本程序，不采曲线也不落会话表，所以 `charge_session` 恒为 0 条，见第四节） |
| 【7】 | 系统整体负载、空闲内存、TF 卡顺序写（`dd bs=1M count=32 conv=fdatasync`） |

它启动 `can_monitor` 用的参数是 `-n -u -v --no-gui`，`charging` 模式下再加 `--auto-start`：

- `-n`：接口在第【1】段已经配好了，不要再通过 netlink 改；
- `--auto-start`：只在 `charging` 模式下加。本程序不会自己上线，只有收到"开始充电"请求后才发 CHM；脚本里没有人去点屏上的「充电」按钮，必须靠这个开关把请求置上。少了它，`can_monitor` 会一直停在空闲态、一帧 CHM 都不发，第【3】段就只会看到待机的心跳与 BSM —— 这正是 `idle` 模式想要的画面；
- `-v`：逐报文日志，判定多帧重组是否成功的依据；
- `-u` / `--no-gui`：不画终端仪表盘、不占 framebuffer，测的是纯 CAN + 存储负载。

脚本结尾那句「如果【3】只看到 18FFF4F4 和 181356F4 两个 ID，说明充电没起来」是针对 `charging` 模式的排查提示；`idle` 模式下看到这两个 ID 正是预期结果。

**板载运行的必要性**：CPU 占用率、SQLite 写入速率、内存占用都跟硬件强相关（Cortex-A7 792 MHz + TF 卡与 x86 + SSD 差一个数量级），PC 或虚拟机上测出的数字不能代表板上工作点。脚本开头检查 `id -u`，不是 root 就直接提示用 `sudo` 退出。
